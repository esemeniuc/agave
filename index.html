How to read the diagrams

Follow the condition, then the action

Hover over a state, arrow, or dotted term to read its explanation. Use Tab for keyboard help. On touch screens, tap once. Press Escape or tap outside to close the help.

Alpenglow must keep one final chain and continue after delays or failed leaders. Each transition serves one of these purposes. Several state machines operate at the same time.

A validator’s vote, its certificate information, and its local execution state are separate facts. For example, it can receive a certificate before the block data. It can also send FinalVote before a final certificate exists.

Read an arrow as follows: when the condition is true, the component performs the action. A return arrow keeps the same state. A dashed arrow can show an emitted event or a proof relationship. Its numbered row explains the meaning.

Local state or actionCondition or eventCertificateSkip or recoveryFinal vote or finality: read the label

Percentages refer to total stake. B and P usually name blocks. The slot s is the current slot. The slot w starts a leader window. Protocol names, such as ParentReady and FinalVote, stay unchanged.

Basic termMeaning
ValidatorOne participant that checks blocks and sends votes. It also receives block data and executes transactions.
StakeThe weight of a validator’s vote. A threshold counts stake, not the number of validators.
SlotOne numbered opportunity for a leader to produce a block.
Leader windowA consecutive group of slots assigned to one leader. The current Agave example uses four slots.
Block / block IDA block contains data and a parent reference. Its block ID identifies the exact block. Different blocks can claim the same slot.
Parent / ancestorThe parent is the preceding block named by a block. Ancestors are the blocks reached through repeated parent links.
Certificate / quorumA certificate proves that a specified stake threshold signed the required votes. A quorum is a group that meets that threshold.
PoolThe validator’s store of verified votes and certificates.

The parent condition

For the first slot of a window, the validator needs ParentReady for the exact parent block. For a later slot, the parent must occupy the preceding slot in that window. The validator must have sent an initial notar vote for that exact parent. These checks keep successive votes on a connected chain.

A block can wait

Agave supplies the Block event after it completes replay. The validator checks stored blocks again after ParentReady or a successful initial notar vote. It checks lower slot numbers first. A parent vote can thus permit votes for successive blocks.

A certificate can arrive first

The validator checks the final-vote conditions after its initial notar vote and after BlockNotarized. Either event can arrive first. Both facts must be present before the validator sends FinalVote.

One first vote per slot

The function trySkipWindow sends SkipVote for each slot in the window that has no first vote. A timeout calls this function only when the expired slot has no first vote. Both fallback handlers also call it. They call it before the ItsOver check for the target slot. Existing first votes stay unchanged.

Why final votes and fallback votes cannot mix

A final vote commits the validator to stop support for a skip or another block in that slot. A fallback vote keeps a recovery path available. The BadWindow and ItsOver checks keep these two actions separate. BadWindow applies to one slot.

A final vote is one signature

A validator can send FinalVote before a final certificate exists. Other validators must also send enough final votes to meet the 60% threshold. A validator that sent SkipVote can still accept a valid finality proof.

2 · When a fallback vote is safe

Fallback votes help the network continue after a delay or conflicting blocks. The validator first checks the initial votes. It must also keep any final-vote commitment.

What the formula terms mean

N(B) is the observed initial notar stake for B. S is the observed initial skip stake. T is the sum of N(B) for all blocks in this slot. These totals count each validator once. They do not include fallback votes.

SafeToNotar

The validator must already have a first vote. That vote must differ from NotarVote for B. Either N(B) is at least 40%, or both other conditions hold. Those conditions are N(B) of at least 20% and N(B) plus S of at least 60%. The block must also meet the data and parent conditions.

Why these block thresholds work

The proof assumes that Byzantine validators control less than 20% of stake. A 40% group thus contains more than 20% correct stake. Their first votes for B prevent another block from obtaining 80% initial support. In the alternative condition, the notar and skip groups also exclude a conflicting fast-final result. The 20% minimum for B ensures that some correct stake supports the block.

SafeToSkip

The validator must have sent an initial notar vote. Subtract the largest block total from all observed initial-vote stake. If the result is at least 40%, SafeToSkip is true. Thus, each possible block has at least 40% observed stake outside its supporters. More than 20% of that stake follows the rules. No block can then get 80% initial support.

Why the parent check remains necessary

For a later block in a window, the validator must get the block and identify its parent. It then needs a notar-fallback certificate, or stronger evidence, for that parent. This check connects fallback support to an available parent chain. The paper also requires stored block data before SafeToNotar. Agave specifically queues later-window blocks for repair and the parent check.

A safe event does not prove a quorum

A SafeToNotar or SafeToSkip event permits a local fallback decision. It does not itself prove 60% support. The validator must still check ItsOver before it sends the fallback vote.

Count stake once

Each percentage is a share of total stake. A mixed certificate can contain initial votes and fallback votes. It counts a validator only once. The validator checks each certificate before it accepts its evidence.

Why 80% permits one-round finality

The proof assumes less than 20% Byzantine stake. An 80% initial-vote group thus includes more than 60% correct stake. The first-vote and fallback rules prevent a competing block certificate or a skip certificate. A second vote round is then unnecessary.

Why two groups of 60% permit finality

The notar certificate proves initial support for B. Correct final voters also commit to stop fallback support for this slot. A 60% final-vote group contains more than 40% correct stake. Less than 60% stake remains available for a conflicting skip or fallback certificate. Thus, those conflicting certificates cannot form.

The two signer groups can differ

Each correct final voter must have sent an initial notar vote for B. The final certificate can use a different selection of signers from a particular notar certificate. If exactly 60% stake ever sends initial notar votes for B, that same stake must supply the final votes.

A notar certificate is not finality

A notar certificate and a skip certificate can exist for the same slot. A notar-fallback certificate also does not make B final. It cannot replace the ordinary notar certificate in the two-round finality rule. The final chain finds which earlier blocks remain and which slots it omits.

Read the dashed arrows as proof relationships

An 80% initial-vote proof also meets the 60% notar requirement. An ordinary notar proof also meets the notar-fallback requirement. The validator does not need three separate messages for these facts. Agave gives the parent tracker any of these sufficient proofs.

A final certificate names a slot

FinalVote signs the slot. The ordinary notar certificate identifies the unique block for that slot. The validator needs both certificates for two-round finality. Either certificate can arrive first. No separate fast-final vote exists.

4 · Why ParentReady permits a new window

ParentReady tells the next leader which block it can use as a parent. The parent needs a certificate. Each slot between that parent and the new window also needs a skip certificate.

Why a parent certificate is necessary

The certificate proves that sufficient stake supports P. The leader can build on P before P becomes final. This permits the next window to start without a separate wait for parent finality.

Why every intervening slot needs a skip certificate

The next block can refer directly to P. A skip certificate permits the chain to pass one intervening slot. The leader needs this permission for every intervening slot. An unsupported gap would leave the chain without the required evidence.

Example

The next window starts at slot 104. Parent P occupies slot 100. A notar certificate for P and skip certificates for 101, 102, and 103 make ParentReady(104,P) true. A certified parent in slot 103 needs no intervening skip certificate.

More than one parent can be ready

Certificates can arrive in any order. A later certificate can make another parent ready for the same window. The earlier ready-parent fact remains valid. The paper lets the leader select any parent that meets the condition. The first ParentReady event starts the timers only once.

Agave additions

Agave tracks usable parents through individual slots. It usually emits ParentReady at the first slot of a leader window. Read the deadline formula

The term blockTime means the time interval for one block. The term networkDelay means the network-delay allowance. The term firstDataTime means the time allowance for the first data set. The time t0 is the first ParentReady time for the window. The slot w is the first slot of that window.

Paper formula

The paper uses Timeout(i) = t0 + Δtimeout + (i − w + 1) × Δblock. Each later slot gets one additional block interval. This gives the leader time to produce successive blocks. The network allowance accounts for message delay.

Why the first shred matters

Agave records FirstShred when it sees the first shred for a slot. That event shows some leader data has arrived. It prevents the crashed-leader event from treating the leader as silent. One shred does not prove that the complete block is available. The ordinary block deadline still applies.

Current 400 ms example

In this checkout, the base network allowance is 400 ms. At a 400 ms block time, the first-data allowance is also 400 ms. Both first-data and first-block events then occur 800 ms after ParentReady. The four block deadlines are 800, 1200, 1600, and 2000 ms after ParentReady. These values describe the implementation example.

Why one timeout can affect later slots

After a required block misses its deadline, the validator can no longer follow the normal sequence of initial notar votes. The helper sends skip votes for every slot in that window that still lacks a first vote. This helps the network reach another leader window. A local timeout does not prove that the leader is faulty.

Why a timeout does not change an existing notar vote

The validator must keep its first vote for each slot. After NotarVote, it needs SafeToSkip to send a skip fallback vote. An ordinary timeout alone does not supply that evidence.

Why the leader can start early

The preceding block usually becomes the ready parent. Early work removes some of the certificate wait from the production path. The leader still needs a ready parent before it completes the normal first-block process.

Happy handover

The ready parent equals the expected parent. The leader keeps the work it already performed. This saves the time that a parent change would require.

Sad handover

The ready parent differs from the expected parent. The leader changes to the permitted parent. The paper ignores earlier slices for execution after this change. Agave stops and drains the old record input before it sends UpdateParent and changes the bank. This prevents old execution records from entering the new execution sequence.

The change has a limit

The paper permits one parent change in the first slot of a window. Later blocks extend their preceding block. This keeps the normal sequence within the leader window connected. The parent change affects unfinished leader work. It does not replace a validator’s first vote.

The feature gate

Agave requires alpenglow_fast_leader_handover and migration permission for block markers before it uses this early-start path. The sad-handover branch is part of that path. It has no separate feature gate here.

Production time after ParentReady

The paper starts the normal first-block interval when a parent is ready. Agave uses the block timer from the ready-parent notification. A parent change can require new execution work, so the normal interval starts from that notification.

Two separate requirements

The certificate proves agreement about the block. Local execution gives this validator the block’s resulting state. Either can finish first. The validator checks the root conditions after a finality event and after a completed-block event.

Why repair uses a hash

Different blocks can claim the same slot. The block hash identifies the data that the certificate refers to. Repair checks slice information and shreds against that identity. Invalid or missing responses cause more requests. The validator must also get missing ancestors to execute the chain.

Why the local first vote is necessary here

Agave checks that its local vote history records a first vote for the slot before it advances the root. That vote can be a skip vote. This check is a local bookkeeping condition. It does not add another network quorum requirement. The validator does not need its own FinalVote or inclusion in the certificate.

Why a hash mismatch stops the validator

Agave can execute the exact final block and still compute an unexpected execution-state hash. This condition means its local state disagrees with the final block’s expected state. The handler stops the validator and saves diagnostic information. Continuing from that state would be unreliable.

Join or rejoin the network

The validator gets a valid finality proof for a block. It repairs that block and its missing ancestors. Those parent links identify the earlier final chain. The paper does not require all earlier vote messages. Agave also uses stored vote history and can add missing ParentReady information during recovery.

Agave implementation

8 · Why standstill recovery repeats messages

Missing messages or long delays can stop new final decisions. Agave then sends stored votes and certificates again. It also increases the network-delay allowance for new window timers.

Why repeat the messages

A validator can miss an earlier vote or certificate. Sending it again gives that validator another opportunity to get the evidence. The sender keeps its original vote choice. The retransmission does not create a second first vote.

Why increase the network allowance

Repeated deadlines can be too short for the actual network delay. A larger allowance gives blocks and certificates more time to arrive. Agave scales only the network allowance. It does not scale the block interval or the first-data production interval.

Which timers change

The multiplier is 1.05 to the power of the number of leader windows since the recorded standstill slot. The network allowance has a one-hour maximum. The change applies when Agave creates a new timer. An existing timer for the same window keeps its original deadline.

What does not change

Standstill does not reduce certificate thresholds. It does not erase first votes or clear ItsOver. These rules protect safety while recovery tries to restore progress. A later final slot clears the standstill state. A restored identity with a root above the recorded slot also clears that old standstill state.

Protocol terms and code events

Technical terms

TermMeaning
NotarVote / notar voteThe initial vote that supports one exact block. To notarize a block is to establish its ordinary notar certificate.
SkipVote / skip voteThe initial vote that supports progress past a slot. One skip vote does not decide the slot.
Fallback voteAn additional vote sent after an initial vote when the specified safe condition holds. It helps form a block or skip certificate.
FinalVote / final voteA second vote that commits its sender to stop fallback support in the slot. It signs the slot number.
Finality / finalizeFinality is the protocol decision that fixes a block and its parent chain. To finalize a block is to establish this decision.
ParentReadyA local event that identifies a parent the new window can use. The parent does not need to be final.
Guard / conditionA check that must pass before an action can occur.
Pending blockA stored block that waits for the parent evidence needed for an initial notar vote.
Replay / bank / rootReplay executes the block’s transactions. A bank holds the resulting local state. The root marks the validator’s fixed local chain.
Shred / slice / repairA shred is a piece of encoded block data. A slice groups block data before shredding. Repair retrieves missing data by block identity.
Hash / Merkle proofA hash identifies data through a cryptographic calculation. A Merkle proof connects one data item to the expected aggregate hash.
Byzantine validatorA validator that can break protocol rules. The safety explanations assume that such validators control less than 20% of total stake.
Emit an event / handlerTo emit an event is to send an internal notification. A handler runs the actions for that notification.
Broadcast / retransmitTo broadcast is to send a message to the other validators. To retransmit is to send the same message again.
Happy handover / sad handoverHappy handover keeps early work because the ready parent matches. Sad handover changes the parent and discards the old execution work.
Feature gate / migrationA feature gate controls whether a protocol feature can run. Migration is the change from the earlier consensus system to Alpenglow.

Stored state flags

The validator can hold several state flags for one slot. Adding one flag does not erase the other flags. Local root advancement lets the validator remove obsolete state.

FlagMeaning
ParentReady(P)The validator has the evidence needed to use P as a parent. Several parents can meet this condition.
VotedThe validator sent its first vote for the slot: NotarVote or SkipVote.
VotedNotar(B)The validator’s first vote supports the exact block B.
BlockNotarized(B)The validator has an ordinary notar certificate for B. This fact does not describe its own vote.
BadWindowThe validator sent SkipVote or a fallback vote in this slot. It cannot then send FinalVote for that slot.
ItsOverThe validator sent FinalVote for the slot. It cannot send another new vote for that slot.

Why Agave ignores old events

Agave ignores most slot events at or below its effective local root. It ignores Standstill when the event slot is below that root. It always considers SetIdentity. These checks keep old messages from restarting obsolete work.

Rewards use a separate path

The leader in slot s+8 can include initial notar and skip vote aggregates for slot s. These reward aggregates do not need a consensus quorum. They prove participation for payment. They do not cause ParentReady or finality. Source: SIMD-0326 rewards.
